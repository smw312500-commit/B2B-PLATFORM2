2026-06-04
========================================

Agent 간 보고 채널 UI 기획 확정.

목적:
  각 회사 DB를 플랫폼에 직접 넘기는 방식이 아니라,
  각 agent가 자기 DB를 보고 판단한 결과만 플랫폼에 보고하는 구조를 화면에서 명확히 보여주기 위함.

방식:
  자유채팅이 아니라 "보고 전용 채널"로 만든다.
  실제 업무 처리는 기존 API JSON 보고로 유지하고,
  화면에서는 그 보고 이벤트를 채팅 말풍선/타임라인처럼 보여준다.

중요 원칙:
  - 사람이 임의 문장을 입력해서 업무를 처리하지 않음
  - 채팅 텍스트를 파싱해서 비즈니스 로직을 돌리지 않음
  - API payload가 원본 데이터이고, 채팅 UI는 사람이 이해하기 쉽게 요약해서 보여주는 표현 계층

플랫폼 채널 구조:
  단체 채팅처럼 만들지 않고, 플랫폼 기준 1:1 채널로 분리한다.
    - 플랫폼 - 라벨
    - 플랫폼 - 물류
    - 플랫폼 - 지퍼단추
    - 플랫폼 - 옷감

각 agent 화면:
  각 회사는 자기 채널 하나만 본다.
    - 라벨agent: 라벨 - 플랫폼
    - 옷감agent: 옷감 - 플랫폼
    - 지퍼단추agent: 지퍼단추 - 플랫폼
    - 물류agent: 물류 - 플랫폼

보고 채널에 표시할 이벤트:
  생산사 -> 플랫폼:
    - 생산 스케줄 보고
    - 재조정 보고
    - BL/원자재 입고 보고
    - 출고완료 보고

  플랫폼 -> 물류:
    - 픽업 요청
    - 배차 요청
    - 납기 위험 화물 알림
    - 귀로배정 후보 알림

  물류 -> 플랫폼:
    - 배차 확정 보고
    - 기사/차량 배정 결과
    - 픽업일 계산 결과
    - 왕복/귀로배정 결과
    - 배송 완료 신호

포트폴리오 관점:
  이 UI는 멀티 에이전트 오케스트레이션 과정을 사람이 추적할 수 있게 보여주는 핵심 화면이다.
  "각 agent가 무엇을 판단했고, 플랫폼이 어떤 보고를 받아 다음 agent로 넘겼는지"를 설명하기 위한 장치로 사용한다.

2026-06-09
========================================

플랫폼 역할 범위 다시 정리.

지금 우선순위는:
  1. 생산사 완료 목록 보고 수신
  2. 물류사 가용 기사/차량 확인
  3. 플랫폼이 매칭 수행

중요 구조 원칙 재확인:
  플랫폼은 각 회사 DB를 직접 읽지 않는다.
  각 회사 agent가 자기 DB를 보고 판단한 결과만 플랫폼에 보고한다.

즉,
  - 생산사 -> 플랫폼: 완료/입고/재조정/납기판단 보고
  - 물류사 -> 플랫폼: 기사 가용정보 / 차량 / 배차결과 / 배송완료 보고
  - 플랫폼 -> 물류사: 픽업/배차 요청

직접 DB 연동 방식이 아니라 agent orchestration 방식으로 계속 간다.

플랫폼 기능 진행 상황:
  - 1:1 보고 채널 UI/DB 구조 완성
  - 완료 이벤트만 보고 채널에 보이도록 필터링 조정
  - 물류 가용 기사/차량 조회 API 연결
  - 자동 배차 후 기사/차량/귀로판단을 dispatch에 반영

회사 주소 처리 방향도 정리:
  초기에는 플랫폼 DB company_info에 구 단위 주소만 placeholder로 넣어둔다.
  최종 구조는 물류agent가 회사 주소/기사정보를 플랫폼에 보고하고,
  플랫폼은 그 보고값 기준으로 매칭한다.

company_info 임시 주소 반영:
  - 옷감사: 서울시 구로구
  - 케어라벨사: 서울시 금천구
  - 지퍼단추사: 서울시 구로구
  - 물류사: 서울시 금천구

검증/정리:
  - 플랫폼 backend compile 확인
  - 플랫폼 frontend build 확인
  - 기존 company_info 값도 실제 DB에 동기화 완료

라벨사 연동 기준을 플랫폼 기준으로 다시 고정.

플랫폼이 라벨사에서 받아야 하는 보고 경로:
  - 수입 보고: POST /api/agent-report/import
  - 수출 보고: POST /api/collected-release

플랫폼 채팅창에서 실제 조회하는 경로:
  - GET /api/report-channels
  - GET /api/report-channels/label/messages

라벨 디버깅 기준도 정리:
  - GET http://localhost:8001/agent/status
  - platform_report_status 보면 라벨agent가 현재 무엇을 보고 대상으로 잡는지 확인 가능

이 계약을 플랫폼 세션 지시문과 지시이력에 반영함.

라벨 수입/수출 payload 문제 분석 결과:
  - 수입 품목(material)은 라벨 쪽에서 이미 보내고 있고 플랫폼도 수신 가능
  - 수출 품목은 라벨 쪽에서 명시적 item_name 없이 보내던 문제가 있었음
  - 그래서 플랫폼에서 label_code로만 대체 저장되던 구간 확인

수정 방향:
  라벨agent 출고완료 보고 payload에
  - item_name
  - quantity
  - status
  - company_name
  - 숫자형 company_id
  를 명시적으로 포함하도록 보강

플랫폼 보고방 문제도 같이 정리:
  증상:
    - 라벨 입고만 보이는 것처럼 보임
    - 일부 출고완료 메시지 상태/단위/요약이 깨져 보임
    - 채팅 요약이 실제 payload를 충분히 설명하지 못함

원인:
  - 완료 이벤트 필터에는 맞지만 stored payload 일부가 과거 포맷/깨진 값 상태였음
  - collected_release / report_message 안에 status, unit, summary가 깨진 데이터 존재
  - 플랫폼 채팅 카드가 수출 payload를 충분히 해석하지 못함

플랫폼 쪽 보정:

라벨사 ↔ 플랫폼 보고 방식 정리.

라벨사 플랫폼 채널은 회사 내부 전부를 보내지 않고,
  - 자재입고 = 수입
  - 완료물건 = 수출
이 2가지만 보고하는 형태로 정리.

수출 완료 보고는 개별 행 단위가 아니라
동일 납기일 기준 묶음 1건으로 보는 방식으로 정리.
예: 2026-06-14 납기 완료건 전체 → 수출 묶음 1건

플랫폼/물류 연결에 필요한 최소 데이터는 반드시 포함:
  - 수입: BL 번호, 선적항, 도착항, 최종도착지, 수령위치, 중량
  - 수출: 총중량, 총 박스수, 납기 묶음 기준 완료수량, 패킹리스트

라벨사 BL 파서는 mock BL PDF의 항구 3열 구조를 읽어
  Port of Loading / Port of Discharge / Final Place of Delivery
를 정확히 분리하도록 보강.

패킹리스트 UX도 확장:
  날짜 범위 전체 추출 외에,
  완료목록 체크박스 선택건만 별도 패킹리스트로 추출 가능하게 함.

API 호출 원칙 재확인:
