========================================
[001] 분산 DB 환경에서의 데이터 불일치 문제
========================================

발견일: 2026-05-31
발견 경위: 외부 AI(Gemini) 코드 리뷰 지적

[ 문제 ]
생산사가 "완료 버튼" 클릭 시 두 가지 작업이 순서대로 실행됨:
  1단계: 자사 DB 재고 차감
  2단계: 플랫폼 서버로 출고완료 신호 POST

1단계 성공 직후 플랫폼 서버가 일시적으로 응답 불가 상태가 되면:
  → 재고는 이미 차감됨 (자사 DB)
  → 플랫폼은 출고된 사실을 모름 (수집 실패)
  → 두 DB 간 데이터 불일치 발생

[ 원인 ]
5개 독립 MySQL DB 구조 + HTTP API 기반 데이터 전달
→ 네트워크 단절 / 서버 재시작 / 타임아웃 시 원자성 보장 불가

[ 해결 방안 ]
platform_sender.py에 전송 실패 시 재시도 메커니즘 구현:
  - 최대 3회 재시도 (1초 간격)
  - 3회 실패 시 로컬 DB에 "전송실패" 상태 기록
  - 서버 재시작 시 "전송실패" 건 자동 재전송

[ 포폴 설명 ]
"5개 독립 DB 구조에서 발생하는 분산 트랜잭션 문제를 인지하고,
 전송 실패 시 재시도 메커니즘과 실패 상태 기록으로
 데이터 유실을 방지하는 내결함성(Fault-tolerance) 아키텍처 적용"

구현 상태: 예정

5개 agent 동시 실행 시 프론트엔드 포트 충돌:
  - 라벨agent (5173) vs 지퍼단추agent (5173) → 충돌

각 세션이 독립적으로 개발되면서 포트 번호 중복 할당

[ 해결 방안 ]

  플랫폼  백엔드 8000 / 프론트 5174
  라벨    백엔드 8001 / 프론트 5173
  옷감    백엔드 8002 / 프론트 3000
  지퍼단추 백엔드 8003 / 프론트 5175 (변경)
  물류    백엔드 8004 / 프론트 3001 (변경)
  BL파서  백엔드 8010

  지퍼단추: vite.config.js port 5173 → 5175
  물류: vite.config.js port 3000 → 3001

[ 포폴 설명 ]
"다중 agent 동시 실행 환경에서 포트 충돌 문제를 발견하고
 전체 포트 체계를 재설계하여 5개 서비스 동시 구동 환경 확립"

[003] 플랫폼-물류 연결 단절 문제
========================================

발견일: 2026-05-31
발견 경위: 전체 데이터 흐름 코드 리뷰 중 발견

[ 문제 ]
플랫폼이 생산사 3곳 출고완료를 감지하고 dispatch 테이블을 생성하지만
물류 agent에 신호를 보내지 않아 물류 시스템이 화물을 인식하지 못함:
  플랫폼 dispatch_auto.py → dispatch 생성 후 종료
  물류 /api/platform/signal → 엔드포인트 존재하나 아무도 호출 안 함

[ 원인 ]
플랫폼-물류 연결 구간이 기획에는 있었으나 구현 누락

[ 해결 방안 ]
dispatch_auto.py에 dispatch 생성 직후 물류 agent로 POST 전송 추가:
  → POST http://localhost:8004/api/platform/signal
  → body: company_id, company_name, destination, due_date, pickup_date

[ 포폴 설명 ]
"전체 데이터 흐름 검증 중 플랫폼→물류 구간 단절을 발견,
 자동 신호 전송 로직 추가로 생산완료→배차자동등록 전체 체인 연결 완성"

[004] 이동시간 로직 단순화 문제
========================================

발견일: 2026-05-31
발견 경위: 귀로 최적화 로직 검토 중

[ 문제 ]
물류 AI의 이동시간 계산이 출발지 무관 무조건 1일로 고정:
  TRAVEL_DAYS = {"인천항": 1, "부산항": 1}
  → 부산 → 부산항(1시간)과 서울 → 부산항(5시간)이 동일 처리
  → 픽업일 계산 부정확 → 귀로 연결 로직도 부정확

[ 원인 ]
초기 구현 시 단순화된 기본값 사용, 고도화 미적용

[ 해결 방안 ]
출발지 + 도착지 조합별 이동시간 매트릭스 적용:
  부산 → 부산항: 1시간 (당일)
  부산 → 인천항: 6시간 (1일)
  서울 → 인천항: 1시간 (당일)
  서울 → 부산항: 5시간 (1일)
  인천 → 인천항: 0.5시간 (당일)
  인천 → 부산항: 5시간 (1일)

  픽업일 계산:
    이동시간 < 3시간 → 납기일 - 1일
    이동시간 >= 3시간 → 납기일 - 2일

[ 포폴 설명 ]
"물류 AI의 단순화된 이동시간 로직을 출발지-도착지 매트릭스로 고도화,
 실제 운송 시간을 반영한 정확한 픽업일 산출 및 왕복 최적화 정확도 향상"

구현 상태: 예정

========================================
[005] 귀로 최적화와 데이터 실시간성 문제
========================================

발견일: 2026-05-31
발견 경위: 귀로 최적화 설계 중 데이터 일관성 리스크 검토

[ 문제 ]
귀로 최적화를 위해 플랫폼이 "생산중" 상태를 실시간 모니터링할 경우:
  - 생산 진행률(300개/1000개 완성 등)을 지속 전송 시
  - 서버 다운 중간에 진행률 데이터 유실 → 플랫폼과 실제 수치 불일치
  - 잘못된 귀로 계산으로 기사 동선 최적화 오류 발생 가능

[ 원인 ]
실시간 진행률 동기화는 분산 환경에서 데이터 불일치 위험이 높음

[ 해결 방안 ]
귀로 최적화에 필요한 데이터를 "진행률"이 아닌 "due_date"로 단순화:
  - 생산 시작 시: { status: "생산중", due_date: "5/2", qty: 1000 } 1회 전송
  - 중간 진행률: 플랫폼 미전송 (자사 DB에서만 관리)
  - 완료 시: { status: "출고완료" } 전송 (현재 구조 유지)

  due_date는 생산 시작 시 고정되는 값 → 서버 장애와 무관하게 신뢰 가능
  플랫폼 AI는 due_date 기준으로만 귀로 가능 화물 예측

[ 포폴 설명 ]
"분산 환경에서 실시간 데이터 동기화의 위험성을 인지하고,
 귀로 최적화에 필요한 데이터를 '진행률' 대신 '납기일(due_date)'로
 단순화하여 데이터 일관성을 유지하면서 기능을 구현하는 설계 채택"

구현 상태: 예정

========================================
[006] 멀티 에이전트 보고 구조 설계 결정
========================================

발견일: 2026-05-31
발견 경위: 플랫폼이 귀로 최적화를 위해 각사 DB를 모니터링해야 하는지 검토 중

[ 문제 ]
플랫폼 AI가 물류 최적화를 하려면 각사 생산 현황을 알아야 함.
초기 설계: 플랫폼이 각사 DB를 직접 읽거나 raw 데이터를 수집
→ 수백 행 데이터를 GPT에 넣어야 함 (토큰 낭비)
→ 플랫폼이 각사 도메인 로직까지 이해해야 함
→ DB 스키마 변경 시 플랫폼 코드도 수정 필요

[ 원인 ]
DB 직접 조회 방식은 결합도가 높고 AI 처리 비용이 큼

[ 해결 방안 — 멀티 에이전트 보고 구조 채택 ]

각사 AI (도메인 전문가):
  - 자사 생산 스케줄 관리 (시작~완료 예정 시각)
  - 돌발상황 감지 → 자동 재조정 → 플랫폼에 업데이트 보고
  - BL 입고 감지 → 입고 예정일 플랫폼 전송
  - 플랫폼에 보내는 것: 이미 판단된 요약 정보

  예) "지퍼사 AI 보고: 5/2 14:00 완료예정, 정상"
      "옷감사 AI 보고: 5/3 09:00 완료예정, 원사 부족 주의"

플랫폼 AI (오케스트레이터):
  - 각사 AI 보고서만 받아서 종합 판단
  - 수출 화물 + 수입 화물 타이밍 계산
  - 물류에 시간 단위 정밀 지시
  - DB raw 데이터 직접 처리 안 함

[ DB 읽기 vs AI 보고 비교 ]
  항목              DB 직접 읽기     AI 보고 방식
  GPT 토큰 비용     높음             낮음 (1/10 수준)
  도메인 판단       플랫폼이 다 함   각사 AI가 함
  DB 스키마 변경    플랫폼 코드 수정  영향 없음
  판단 정확도       낮음             높음 (전문성 반영)

[ 포폴 설명 ]
"플랫폼 AI가 raw DB 데이터를 직접 처리하는 대신,
 각사 도메인 AI가 판단한 요약 보고서를 플랫폼 AI가 수신하는
 멀티 에이전트 오케스트레이션 구조를 채택.
 GPT 토큰 비용 절감 + 각사 도메인 전문성 활용 + 느슨한 결합 실현."

구현 상태: 예정

[007] 분산 메시지 식별을 위한 공통 ID(Report ID) 도입
========================================

발견일: 2026-06-10
발견 경위: 플랫폼 서버 일시 장애 시 에이전트 보고 데이터 누락 확인

[ 문제 ]: 에이전트가 보낸 요약 보고서가 플랫폼에 도착했는지 확인할 방법이 없고, 재전송 시 중복 처리될 위험이 있음
[ 원인 ]: 통신을 추적할 고유 식별자(Transaction ID) 부재로 인한 정합성 위기
[ 해결 방안 ]: 
  - 모든 보고 이벤트 생성 시 `report_id`를 강제 부여
  - 에이전트 DB에 이 ID를 저장하고, 플랫폼 전송 시 payload에 포함
  - 실패 건 자동 재시도 로직(platform_retry.py) 구현
[ 포폴 설명 ]: 
  "분산 아키텍처에서 발생할 수 있는 메시지 유실 및 중복 문제를 방지하기 위해, 
   에이전트와 플랫폼 간의 공통 식별자(Report ID) 체계를 설계했습니다. 
   이를 통해 전송 실패 시에도 동일 ID를 활용한 안전한 재시도가 가능해졌으며, 
   시스템 간 데이터 정합성을 보장하는 내결함성을 확보했습니다."

구현 상태: 완료

========================================
[008] 재시도 성공 후 에이전트 측 상태 동기화 실패 (보고 채널 상태 불일치)
========================================

발견일: 2026-06-10
발견 경위: 라벨agent "Agent 보고 채널" UI에서 W2WPM10GY 수출 보고가
          "플랫폼 보고 대기"(06.09 13:44)로 표시되어 있으나,
          플랫폼 DB에는 이미 수신 완료되어 있는 것을 확인

[ 문제 ]:
  - 라벨agent DB(label_platform_report_event id=22, item_ref=W2WPM10GY,
    report_type=release)가 status='플랫폼 보고 대기', report_id=NULL 상태로
    06-09 13:44:25 이후 한 번도 갱신되지 않음
  - 반면 플랫폼 DB(collected_release id=14 / report_message id=24)에는
    동일 W2WPM10GY 출고 데이터가 2026-06-10 15:10:06에 정상 수신/저장됨
    (단, 이 payload에도 report_id/source_report_id가 NULL)
  - 즉 데이터는 플랫폼에 도착했는데, 라벨agent 화면은 여전히 "대기"로 표시

[ 원인 ]:
  - event id=22는 06-09 13:30~13:44 플랫폼 다운타임([007] 발생 이전) 때
    실패해 멈춘 건으로, report_id 기능 도입 전에 생성되어 report_id=NULL
  - platform_retry.py 백그라운드 재시도 루프가 이 옛 payload를
    06-10 15:10경 재전송 → 플랫폼은 정상 수신(collected_release 생성)
  - 하지만 이후 finish_report(event_id, True, ...) 호출이 라벨agent DB에
    반영되지 않아(커밋 단계 실패 추정) event 상태가 "전송완료"로 바뀌지 않음
  - report_id가 없는 구버전 payload이므로 [007]의 신규 dedupe 로직도
    적용되지 않음 → 재시도 루프가 계속 살아있다면 동일 데이터가
    플랫폼에 중복 저장될 위험도 있음

[ 해결 방안 ]: 검토 중
  - finish_report 커밋 실패 원인 추적 (예외 로깅 추가)
  - report_id가 없는 구버전 이벤트(15~22) 정리/마이그레이션
  - report_id 없는 payload에 대한 dedupe 보강 여부 검토

구현 상태: 미해결 (검토 중)

========================================
[009] 물류 연동을 직접 전달이 아닌 플랫폼 내부 판단 레이어로 분리
========================================

발견일: 2026-06-12
발견 경위: 물류agent가 기사/차량 DB 스냅샷을 플랫폼에 넘기고,
          라벨agent 출고완료 보고를 받은 뒤 플랫폼이 물류agent에 배차 요청을 보내는 구조 검토 중

[ 문제 ]:
라벨agent 출고완료 보고를 받자마자 플랫폼이 바로 물류agent로 API를 쏘면,
그 시점의 물류 기사/차량 상태, 귀로 가능 여부, 납기 여유, 중복 요청 여부를
종합 판단하기 어렵다.

[ 원인 ]:
수신 API나 채팅 UI가 곧바로 물류 전송까지 담당하면
데이터 수신, 판단, 외부 전송 책임이 한 곳에 섞인다.
이 경우 나중에 물류 조건이 늘어나거나 AI 판단을 추가할 때 구조가 쉽게 꼬인다.

[ 해결 방안 ]:
플랫폼agent 안에 별도 판단 레이어를 둔다.
별도 서버를 만들지는 않고, 플랫폼 내부 서비스로 `dispatch_planner` 또는
`orchestration_service` 역할을 분리한다.

흐름:
  1. 물류agent → 플랫폼에 기사/차량 DB 스냅샷 전송
  2. 라벨agent → 출고완료 보고 + 패킹리스트 전송
  3. 플랫폼agent → 두 데이터를 DB에 저장
  4. 플랫폼 내부 판단 서비스 → 라벨 출고상황 + 물류 가용상황 종합 계산
  5. 판단 결과 → 물류agent API로 전송
  6. 플랫폼-물류 채팅창 → 배차요청/판단결과만 보고 형태로 표시

[ 포폴 설명 ]:
"플랫폼이 단순 API 중계기가 아니라, 생산사 출고완료 데이터와 물류 가용 기사 데이터를
 내부 판단 레이어에서 종합해 배차 요청을 생성하는 오케스트레이션 구조를 설계했습니다.
 채팅 UI는 로직 처리 공간이 아니라 판단 결과를 보여주는 보고 채널로 분리했습니다."

구현 상태: 예정

========================================
[010] 비즈니스 문서의 경직성과 실무 수정 요구의 충돌
========================================

발견일: 2026-06-12
발견 경위: 발주서 생성 기능 테스트 중 실무자 인터뷰 모사

[ 문제 ]: 
기존 PDF/CSV 방식은 데이터 무결성은 높으나, 기업 간 거래(B2B)에서 발생하는 '예외 상황(특약 조항 추가, 사과 문구 수정)'에 대응할 수 없음. 
결과물이 너무 딱딱하여 실무자가 시스템 외부에서 문서를 새로 만드는 비효율 발생.

[ 원인 ]: 
PDF는 '최종 확정본' 성격이 강해 배포 후 수정이 불가능하고, CSV는 '데이터'일 뿐 '문서'로서의 격식이 없음.

[ 해결 방안 ]: 
가변성이 높은 '대외 공문' 및 '구매 발주서'에 한해 DOCX(Word) 생성 로직 도입.
AI가 초안(Draft)을 완벽하게 작성해주되, 마지막 5%의 문구 수정을 사람(담당자)에게 맡기는 'Human-in-the-loop' 업무 흐름 설계.

[ 포폴 설명 ]: 
"단순히 기술적으로 편리한 포맷(JSON, CSV)만 고집하지 않고, 실제 비즈니스 현장에서 '수정 가능한 문서'가 갖는 법적/실무적 가치를 이해하여 DOCX 자동 생성 기능을 아키텍처에 포함시켰습니다."
