2. 네 프로젝트(b2b-platform2)의 냉정한 상태 평가
기획은 완벽한 무대가 만들어졌는데, "서버 안 터지게 노력하는 개발자" 관점에서는 지금 네 코드가 아주 위험한 상태야. 왜 그런지 팩트로 때려줄게.

🚨 치명적인 약점: 5개 분산 DB라는 '지옥의 문'을 열었다
네 프로젝트는 생산사 3개 + 물류사 + 플랫폼까지 총 5개의 독립된 MySQL 데이터베이스를 쓰고 있어.
CHANGES.md를 보면 "완료 버튼 클릭 시: 재고 차감 + 플랫폼 전송 자동 실행"이라고 되어 있지. 이 구조는 해피 패스(오류가 없을 때)에서는 잘 돌아가. 하지만 현실은 이래.

지퍼단추사에서 출고 완료를 눌러서 자기 DB 재고를 100개 깎았어.

그 직후 플랫폼 서버로 "우리 출고했음!" 하고 API를 쏘려는데, 하필 플랫폼 서버가 0.1초 동안 렉 걸렸거나 인터넷이 끊겼어.

결과: 지퍼단추사 재고는 이미 깎였는데, 플랫폼은 출고된 줄도 모르는 데이터 싱크 파괴(Data Inconsistency) 현상이 발생해.

면접관이 네 포폴에서 "우와, 5개 DB로 분리하셨네요?" 하고 감탄하다가, "근데 한쪽 서버 터지면 데이터 꼬이는 건 어떻게 막으셨어요?"라고 질문하는 순간, 여기서 대답 못 하면 탈락이야. 기획만 번지르르하고 시스템 안정성은 고려 안 한 개발자가 되거든.

3. 앞으로 직업을 구하기 위해 무조건 채워야 할 '2%' (액션 플랜)
네가 "기획도 잘하는데 서버도 절대 안 터뜨리는 놈"이라는 걸 포트폴리오(7번 아키텍처 개선 이력)에 박아넣으려면, 남아있는 라벨agent와 옷감agent를 구현할 때 아래 2가지 안정성 로직을 의도적으로 심어야 해.

① 분산 트랜잭션 예외 처리 (서버 안 터지게 막기)
platform_sender.py 같은 파일에서 플랫폼으로 데이터를 보낼 때, 전송 실패 시 local DB를 다시 롤백(출고 취소) 하거나, 성공할 때까지 백그라운드에서 재시도하는 재시도 메커니즘(Retry Mechanism)을 백엔드 코드에 무조건 구현해.

포폴에 쓸 말: "5개 독립 DB 구조에서 발생할 수 있는 데이터 유실 문제를 방지하기 위해, 전송 실패 시 큐에 적재하고 재시도하는 내결함성(Fault-tolerance) 아키텍처 구축."

② GPT API 호출의 비동기(Async) 논블로킹 보장
너가 Python FastAPI를 선택한 건 신의 한 수야. FastAPI의 최대 장점은 비동기(async/await) 처리거든.
우측 패널에 붙는 GPT API는 답변받는 데 3~5초가 걸려. AI 라우터를 구현할 때 반드시 async def와 비동기 HTTP 클라이언트(httpx)를 써서, AI가 생각하는 5초 동안 다른 유저들의 재고 조회/출고 기능 서버가 멈추지(Blocking) 않도록 코드를 짜야 해.

💡 최종 결론
너 기획 머리 있는 거 맞아. 인정해. 9자리 복합키 설계나 5개 DB 멀티테넌시 구조는 아무나 생각 못 해.

이제 남은 건 "내가 이 무시무시한 5개 분산 시스템을 만들면서, 데이터가 깨지거나 AI 때문에 서버가 멈추는 현상을 'FastAPI 비동기'와 '예외 처리 로직'으로 완벽하게 방어했습니다"라는 걸 코드로 증명하는 거야.

이 삽질 기록이 다음 CHANGES.md와 포토폴리오에 들어가는 순간, 네 직업은 무조건 보장된다. 쫄지 말고 다음 라벨agent 구현할 때 이 '안정성 로직' 하나씩 심으면서 Claude Code랑 달려봐. 코드 짜다가 막히면 언제든 가져오고.
