[2026-06-04 13:53] Agent 간 1:1 보고 채널 UI 추가
----------------------------------------
지시: 플랫폼agent에 각 agent와 API 보고 이벤트를 채팅처럼 확인하는 1:1 보고 채널을 만들 것

  목적:
    생산사/물류사가 자기 DB를 플랫폼에 넘기는 방식이 아니라,
    각 agent가 자기 상황을 판단한 결과만 플랫폼에 보고하는 구조를 화면에서 확인 가능하게 만든다.

  중요한 원칙:
    - 자유채팅 기능이 아니다.
    - 실제 업무 처리는 기존 API JSON 보고로 한다.
    - 채팅 UI는 API 보고 이벤트를 말풍선/타임라인처럼 보여주는 화면이다.
    - 채팅 텍스트를 파싱해서 비즈니스 로직을 돌리면 안 된다.

  플랫폼 채널 구조:
    단체 채팅처럼 만들지 말 것.
    아래 4개 1:1 채널을 분리해서 보여줄 것.
      - 플랫폼 - 라벨
      - 플랫폼 - 물류
      - 플랫폼 - 지퍼단추
      - 플랫폼 - 옷감

  기록 대상 이벤트:
    - 라벨/옷감/지퍼단추 -> 플랫폼
      · /api/agent-report/schedule
      · /api/agent-report/reschedule
      · /api/agent-report/import
      · /api/collected-release
    - 플랫폼 -> 물류
      · /api/platform/signal 전송
      · 배차 요청
      · 픽업 필요 보고
      · 납기 위험 화물 알림
      · 귀로배정 후보 알림
    - 물류 -> 플랫폼
      · 배차 확정 정보
      · 배송 완료 신호
      · 왕복/귀로배정 결과

  권장 데이터 구조:
    report_message 또는 agent_message 테이블/모델을 추가해도 됨.
    필드 예시:
      - id
      - channel: label / logistics / zipper / fabric
      - direction: inbound / outbound
      - source_agent
      - target_agent
      - event_type
      - related_code
      - title
      - summary
      - payload_json
      - status
      - created_at

  백엔드 작업:
    - 기존 agent_report 수신 시 report_message에도 기록
    - collected_release 수신 시 해당 생산사 채널에 기록
    - 물류agent로 signal 전송 시 플랫폼-물류 채널에 outbound 기록
    - 물류agent 완료/상태 수신 시 플랫폼-물류 채널에 inbound 기록
    - 조회 API 추가
      예:
        GET /api/report-channels
        GET /api/report-channels/{channel}/messages

  프론트 작업:
    - 플랫폼 UI에 "Agent 보고 채널" 또는 "보고 채널" 탭 추가
    - 4개 채널을 분리해서 표시
    - 단톡방 느낌이 아니라 플랫폼과 각 agent 간 1:1 업무 보고 화면처럼 구성

  주의:
    - 이 기능은 오케스트레이션 과정을 보여주기 위한 핵심 포트폴리오 UI다.
    - 구현 후 결과에 수정 파일, 추가 API, 추가 테이블 여부를 기록할 것.

  - 귀로 가능 기사와 납기 임박 건이 보이도록 판단 사유(reason/decision_log)를 남긴다.
  - logistics_bridge는 판단 결과를 물류agent API로 전달하는 역할만 맡는다.
  - 플랫폼-물류 채팅창에는 계산 과정 전체가 아니라 배차요청/배차확정/귀로판단결과만 보고 형태로 표시한다.

[2026-06-15] 분석 페이지와 AI 인사이트 영역 분리 지시
지시: 플랫폼의 분석/인사이트 기능을 하나로 섞지 말고, "분석" 영역과
  "AI 인사이트" 영역으로 분리해서 설계할 것.

1) 분석 영역
  목적:
    - 생산회사 agent들이 플랫폼에 보고한 데이터를 기준으로 객관적인 숫자/표/그래프를 보여준다.
    - AI가 바로 결론을 말하기 전에, 어떤 데이터 근거가 있는지 사람이 확인할 수 있게 한다.

  생산사에서 넘어오는 핵심 정보:
    - 자재 발주일
    - 자재 납기일
    - 실제 자재 입고일 또는 입고예정일
    - 자재 공급회사
    - 가공품 생산시작일
    - 가공품 생산완료일
    - 가공품 납기일
    - 생산품 내용
      · 패킹리스트에서 수량, 박스수, 중량, 품목 구성 확보 가능
    - 라벨/의상 정보
      · 라벨코드에서 계절, 성별, 원단, 옷종류, 스타일/색상 계열 확보 가능

  분석해야 할 대표 지표:
    - 자재 입고 지연일 = 실제 입고일 - 자재 납기일
    - 자재 리드타임 = 실제 입고일 - 자재 발주일
    - 공급사별 평균 지연일
    - 공급사별 납기 준수율
    - 생산 소요시간 = 생산완료일 - 생산시작일
    - 생산 납기 여유일 = 생산 납기일 - 생산완료일
    - 생산 납기 압박도
      · 시간이 갈수록 생산완료일이 납기일에 가까워지는지 확인
    - 품목/의류군별 반복 병목
      · 계절/성별/원단/옷종류 기준으로 반복 지연이나 생산시간 증가 확인

  분석 화면 필터:
    - 기간 프리셋: 1개월 / 3개월 / 6개월 / 1년 / 전체
    - 직접 선택: 달력으로 시작일~종료일 선택
    - 분석 대상: 전체 / 공급사 / 생산사 / 자재 / 품목군 / 물류
    - 분석 유형: 자재 납기 / 생산 납기 / 공급사 비교 / 생산성 리스크 / 시즌성

2) AI 인사이트 영역
  목적:
    - 분석 영역에서 계산된 숫자와 근거를 바탕으로 생산기업에게 실행 가능한 솔루션을 제안한다.
    - 이 영역에 외부 AI 에이전트 연동을 검토한다.

  AI가 생성할 인사이트 예시:
    - 자재 공급 날짜가 들쭉날쭉하고 평균 지연일이 크면
      "해당 자재 공급회사 변경 또는 대체 공급사 테스트 발주를 권장"
    - 생산완료일이 납기일 대비 점점 빡빡해지면
      "생산성 저하, 기계 배정 병목, 선제 생산 필요 가능성" 제안
    - 특정 의류군/계절상품에서 반복 병목이 보이면
      "시즌 전 선발주 또는 생산라인 사전 확보" 제안
    - 특정 물류/지역에서 지연이 반복되면
      "플랫폼 연동 물류 또는 다른 배차 전략 사용" 제안

  AI 인사이트 세팅 지시:
    - 외부 AI 에이전트 설치/실행 가능 여부를 확인한다.
    - 플랫폼agent 내부에 AI 호출용 adapter 계층을 준비한다.
      예: backend/services/ai_insight_adapter.py
    - API 키, 설정 파일, 로컬 메모리 파일은 GitHub에 커밋하지 않는다.
    - AI 호출 실패 시 기존 OpenAI 기반 인사이트 또는 규칙 기반 문구로 fallback한다.
    - AI 에이전트는 분석 결과를 해석하는 보조 에이전트이며, 플랫폼 DB나 배차 결과를 직접 수정하지 않는다.
    - 사용자의 채택/보류/무시 피드백은 플랫폼 DB에 저장하고, 다음 AI 인사이트 생성 시 참고 정보로 전달한다.

[2026-06-15] AI 인사이트 에이전트 연동 PoC 지시
지시: 포트폴리오에서 "외부 AI Agent 프레임워크 연동 경험"을 보여주기 위해,

연동 방향:
  - AI 에이전트를 플랫폼 핵심 업무 흐름에 직접 넣지 않는다.
  - 생산사 보고 수신, dispatch_planner 배차 판단, 물류agent API 전송은 기존 플랫폼 로직이 계속 담당한다.

  - 분석 페이지의 숫자/표/그래프는 기존 백엔드 통계 레이어가 계산한다.
  - AI 에이전트는 계산된 분석 결과, 과거 인사이트, 사용자 피드백을 받아

PoC 범위:
  - 외부 AI 에이전트 설치/실행 가능 여부 확인
  - 플랫폼agent에서 AI를 호출하는 adapter 계층 추가 검토
    예: services/ai_insight_adapter.py
  - AI 호출 실패 시 기존 OpenAI 기반 insight 생성으로 fallback 처리
  - AI 응답은 바로 업무 DB를 수정하지 않고, insight draft로만 저장한다.
  - 사용자가 "채택/보류/무시" 피드백을 남기면 플랫폼 DB에 저장하고,
    다음 AI 인사이트 요청 시 참고 정보로 전달한다.

AI 기반 Insight Agent 개념:
  - Memory: 과거 인사이트와 사용자 피드백 저장

  - Feedback Loop: 채택/보류/무시 결과를 다음 추천 톤과 우선순위에 반영

주의:

  - AI 에이전트는 포트폴리오상 "외부 AI Agent 프레임워크 연동"과 "자가개선형 인사이트 컨셉"을 보여주는 보조 계층이다.

  - 설치/운영 복잡도가 크면 1차는 mock adapter로 인터페이스만 고정하고, 실제 AI 실행은 2차로 진행한다.

[2026-06-16] 플랫폼 Q&A 인사이트 엔드포인트 추가 (SQL-based RAG)
지시: 사용자가 자연어로 회사 상태를 질문하면, 플랫폼 DB에 쌓인 보고 데이터를
  회사·주제 기반으로 조회해서 GPT가 분석 답변을 생성하는 엔드포인트를 추가할 것

배경:
  - 플랫폼 DB에는 이미 report_message(전체 보고 이력), collected_release(출고 이력),
    agent_report(스케줄/자재입고/재조정), InsightLog, 4년치 demo CSV가 쌓여 있음
  - 사용자가 "라벨회사 생산성이 어떠냐?"처럼 질문하면, 관련 데이터를 검색해서
    GPT가 "1~2년차 대비 납기일·완료일 격차 축소 → 생산성 하락 / 원인: 자재입고 지연" 같은
    분석 답변을 반환하는 구조
  - 진짜 벡터 RAG까지 갈 필요 없이, 회사명·주제 키워드 → SQL 조회 → GPT 분석 방식으로
    포트폴리오 수준에서 충분한 효과를 낼 수 있음

구현 방향:

1) POST /api/insights/query 엔드포인트 신설
   - 요청: { "question": "라벨회사 생산성이 어떠냐?" }
   - 응답: { "question": ..., "answer": ..., "data_sources": [...], "related_companies": [...] }

2) 회사명 + 주제 키워드 기반 SQL retrieval
   회사명 매핑:
     "라벨" / "케어라벨" → company_id=2
     "옷감"             → company_id=1
     "지퍼단추"         → company_id=3
     "물류"             → company_id=4

   주제 → 조회 대상 테이블/데이터:
     "생산성" / "납기" → collected_release (due_date vs collected_at 비교)
                         + agent_report type=schedule (start_at vs estimated_completion)
                         + production_batches CSV (avg_production_due_buffer_days 추세)
     "자재입고" / "원자재" → agent_report type=import
                              + material_receipts CSV (입고 지연일 추세)
     "물류" / "배차"  → dispatch 테이블 + logistics_performance CSV

3) GPT 분석 프롬프트 구성
   - 회사 이름, 질문, 조회된 데이터(JSON)를 함께 전달
   - "1~2년차(정상 기준선) 대비 최근 수치가 어떻게 변했는가"를 비교 관점으로 분석 요청
   - demo_data 4년치 요약(dataset_summary.json)도 컨텍스트로 첨부

4) 프론트엔드 InsightTab에 질문창 추가
   - 텍스트 입력 → POST /api/insights/query 호출
   - 답변 카드 표시 (답변 본문 + 근거 데이터 출처 태그)
   - 기존 InsightLog 목록 위 또는 별도 섹션으로 배치

대상 파일:
  - backend/routers/insights.py (POST /api/insights/query 추가)
  - backend/services/ai_insight.py (query_insight 함수 추가)
  - frontend/src/components/tabs/InsightTab.jsx (질문창 + 답변 카드 UI 추가)
