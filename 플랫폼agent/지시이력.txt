[2026-06-04 13:53] Agent 간 1:1 보고 채널 UI 추가
----------------------------------------
지시: 플랫폼agent에 각 agent와 API 보고 이벤트를 채팅처럼 확인하는 1:1 보고 채널을 만들 것

  목적:
    생산사/물류사가 자기 DB를 플랫폼에 넘기는 방식이 아니라,
    각 agent가 자기 상황을 판단한 결과만 플랫폼에 보고하는 구조를 화면에서 확인 가능하게 만든다.

  중요한 원칙:
    - 자유채팅 기능이 아니다.
    - 실제 업무 처리는 기존 API JSON 보고로 한다.
    - 채팅 UI는 API 보고 이벤트를 말풍선/타임라인처럼 보여주는 화면이다.
    - 채팅 텍스트를 파싱해서 비즈니스 로직을 돌리면 안 된다.

  플랫폼 채널 구조:
    단체 채팅처럼 만들지 말 것.
    아래 4개 1:1 채널을 분리해서 보여줄 것.
      - 플랫폼 - 라벨
      - 플랫폼 - 물류
      - 플랫폼 - 지퍼단추
      - 플랫폼 - 옷감

  기록 대상 이벤트:
    - 라벨/옷감/지퍼단추 -> 플랫폼
      · /api/agent-report/schedule
      · /api/agent-report/reschedule
      · /api/agent-report/import
      · /api/collected-release
    - 플랫폼 -> 물류
      · /api/platform/signal 전송
      · 배차 요청
      · 픽업 필요 보고
      · 납기 위험 화물 알림
      · 귀로배정 후보 알림
    - 물류 -> 플랫폼
      · 배차 확정 정보
      · 배송 완료 신호
      · 왕복/귀로배정 결과

  권장 데이터 구조:
    report_message 또는 agent_message 테이블/모델을 추가해도 됨.
    필드 예시:
      - id
      - channel: label / logistics / zipper / fabric
      - direction: inbound / outbound
      - source_agent
      - target_agent
      - event_type
      - related_code
      - title
      - summary
      - payload_json
      - status
      - created_at

  백엔드 작업:
    - 기존 agent_report 수신 시 report_message에도 기록
    - collected_release 수신 시 해당 생산사 채널에 기록
    - 물류agent로 signal 전송 시 플랫폼-물류 채널에 outbound 기록
    - 물류agent 완료/상태 수신 시 플랫폼-물류 채널에 inbound 기록
    - 조회 API 추가
      예:
        GET /api/report-channels
        GET /api/report-channels/{channel}/messages

  프론트 작업:
    - 플랫폼 UI에 "Agent 보고 채널" 또는 "보고 채널" 탭 추가
    - 4개 채널을 분리해서 표시
    - 단톡방 느낌이 아니라 플랫폼과 각 agent 간 1:1 업무 보고 화면처럼 구성

  주의:
    - 이 기능은 오케스트레이션 과정을 보여주기 위한 핵심 포트폴리오 UI다.
    - 구현 후 결과에 수정 파일, 추가 API, 추가 테이블 여부를 기록할 것.

[2026-06-11] 플랫폼 채팅창 패킹리스트 첨부 확인/다운로드 + DB 저장 지시
지시: 라벨회사가 출고완료 보고와 함께 보내는 packing_list CSV를 플랫폼 채팅창에서
  첨부파일처럼 확인하고 다운로드할 수 있게 만들 것. 동시에 수신 즉시 플랫폼 DB의
  packing_list 테이블에 저장되도록 보장할 것.

작업 방향:
  - POST /api/collected-release 수신 시 body.packing_list가 있으면 report_message.payload_json에만
    남기지 말고, 반드시 packing_list DB 테이블에도 저장한다.
  - packing_list.csv_base64를 디코딩해 csv_content 원문으로 보관한다.
  - 같은 회사/같은 report_batch_due_date 묶음으로 다시 들어오는 패킹리스트는 중복 생성하지 말고
    최신 CSV로 갱신한다.
  - 플랫폼-라벨 1:1 보고 채널에서 collected_release 메시지에 packing_list가 있으면
    "패킹리스트 CSV" 첨부 카드 또는 다운로드 버튼을 노출한다.
  - 사용자가 채팅창에서 다운로드 버튼을 누르면 플랫폼 DB에 저장된 packing_list CSV를 내려받아
    실제 파일 내용을 확인할 수 있어야 한다.
  - 채팅창에 raw payload만 보여주는 수준에서 끝내지 말고, 사용자가 바로 알아볼 수 있는
    파일명/총수량/총중량/품목수/다운로드 액션을 표시한다.

확인 기준:
  - 라벨agent가 packing_list 포함 출고완료 보고를 보내면 플랫폼 DB packing_list에 행이 생긴다.
  - 플랫폼 보고 채널 UI에서 해당 메시지에 패킹리스트 첨부가 보인다.
  - 다운로드한 CSV 내용이 라벨agent가 보낸 csv_base64 원문과 일치한다.
  - packing_list가 없는 다른 회사/기존 payload는 오류 없이 기존처럼 표시된다.
